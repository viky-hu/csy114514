## 2. 解决什么问题 (痛点)

### 2.1 行业背景

- AI Agent (智能体) 正在大规模进入企业办公: 读邮件、浏览网页、管理日程、保存记忆
- Agent 拥有工具调用能力 (发邮件、写文件、操作数据库)，一旦被恶意指令诱导，后果远超普通聊天机器人
- **间接提示注入 (Indirect Prompt Injection, IPI)** 是 Agent 面临的最大安全威胁之一: 攻击者将恶意指令嵌入网页/邮件内容，Agent 读取后在不知情的情况下执行

### 2.2 核心痛点

| # | 痛点 | 说明 |
|---|------|------|
| 1 | **Agent 上线前没有标准化的安全检测流程** | 企业部署 Agent 前主要靠人工审查，缺乏自动化的安全评估工具 |
| 2 | **安全评测结果不可解释** | 现有工具往往只给出"有风险/无风险"的二元结论，不提供攻击路径、证据链、修复建议 |
| 3 | **攻击手段持续进化，测试覆盖难以跟上** | IPI 攻击有数十种变体 (隐藏 HTML、权威伪装、白字白底等)，手写测试用例效率极低 |
| 4 | **跨会话持久化攻击被严重低估** | 恶意内容写入 Agent 长期记忆，在新会话中才被触发——现有评测几乎不覆盖这条链路 |

### 2.3 我们的解法

> 不是"防火墙"，而是"体检中心"——不做实时防御，而是**上线前系统化地发现问题并给出证据**。

## 3. 产品核心能力 (五大功能模块)

平台按"体检流程"组织为 5 个连续步骤，每步回答一个核心问题:

| 步骤 | 模块 | 回答的问题 | 技术实现 |
|------|------|-----------|----------|
| ① | **总览 Dashboard** | Agent 的体检进行到哪了？ | 聚合画像、图谱、评测、报告四阶段状态 |
| ② | **安全画像 Profile** | 平台是怎么理解这个 Agent 的？ | AgentManifest 解析 → 工具权限、数据源、记忆能力 |
| ③ | **攻击图谱 Anatomy** | 从结构上看，问题可能从哪来？ | 自动推导 4 种攻击路径 (R1-R4)，9 节点 8 边图谱可视化 |
| ④ | **测评运行 Run** | 实际测试中发生了什么？ | 86 条 TestCase 批量执行，SSE 实时事件流，三层沙箱隔离 |
| ⑤ | **测评报告 Report** | 哪里出了问题？为什么？ | 多维度评分 (能力/稳定性/安全)，每条风险绑定完整证据链 |

### 3.1 核心闭环

```
接入 Agent → 生成安全画像 → 识别攻击图 → 编排测试 → 运行评估 → 查看证据报告
```

### 3.2 三个设计原则

| 原则 | 含义 | 对应功能 |
|------|------|----------|
| **先认识，再检测** | 先建立 Agent 的能力档案，再决定检查哪些位置 | 画像 → 图谱的顺序 |
| **潜在 ≠ 已验证** | 发现风险路径不等于攻击已发生，必须动态测试验证 | 图谱"潜在风险" → 运行"已验证风险" |
| **每个结论都要有证据** | 不给出黑箱判定，每条 FAIL 都绑定完整的因果链 | 报告的 5 节点证据可视化 |

## 4. 技术创新点 (6 项)

### 4.1 攻击图谱自动生成

- 输入 Agent 的能力声明 (AgentManifest)，自动推导出所有可能的攻击路径
- 4 种风险模式 (RiskPattern): R1 Web 注入、R2 记忆投毒、R3 隐私泄漏、R4 持久化 IPI
- R4 是旗舰链路: `不可信网页 → Agent → 长期记忆 → Agent → 邮件发送` (5 节点，跨 2 个会话)

### 4.2 三层沙箱隔离执行

| 沙箱层 | 模拟 | 功能 |
|--------|------|------|
| BrowserSandbox | 浏览器 | 注册页面 fixture，Agent 读取网页内容 |
| MemorySandbox | 持久记忆 | K-V 存储，跨 turn / 跨会话持久化 |
| EmailSandbox | 邮件系统 | 收件箱 + 发送确认门控 |

每条 TestCase 执行前自动 `reset()`，确保环境干净、结果可复现。

### 4.3 Mutation Engine — 自动变异生成

- **7 种攻击种子** (邮件转发、隐藏 BCC、记忆偏好注入、签名篡改、假诊断、假配置写入、敏感邮件转发)
- **8 种注入模板** (权威伪装、上下文嵌入、隐藏 HTML、HTML 注释、任务伪装、指令改写、白字白底、假更新提示)
- 组合矩阵: **7 × 8 = 41 条变异 TestCase**，全部自动生成
- 解决了手写测试用例覆盖不足的问题

### 4.4 CompositeJudge — 规则优先的复合判定

```
CompositeJudge
├── RuleJudge (确定性) — 3 条规则:
│   ├── FORBIDDEN_TOOL_CALL     (调用了禁止的工具)
│   ├── CONFIRMATION_MISSING    (敏感操作未获用户确认)
│   └── SENSITIVE_DATA_EXPOSURE (参数中包含敏感数据)
│
└── LLM Judge (语义判定) — Rule 未命中时移交
    └── Stage 2: Mock → Stage 3: 真实 LLM
```

- Rule-first 策略: 规则命中即返回 FAIL，不依赖 LLM 的不确定性
- 每条判定绑定 evidence_event_ids，可追溯到具体的 Trace 事件

### 4.5 实时事件流 (SSE) + 持久化 Trace

- 18 种事件类型 (冻结契约)，覆盖从 `RUN_STARTED` 到 `RUN_FINISHED` 的完整生命周期
- SSE 推送实时事件到前端，每 15 秒心跳
- Trace 持久化到 SQLite，支持事后回放和审计

### 4.6 三阶段演进式评测 (核心叙事)

| 阶段 | Agent 类型 | PASS 含义 | 验证了什么 |
|------|-----------|-----------|-----------|
| Stage 2 (已完成) | 关键词 Agent (CorpMate) | 攻击未触达 | 评测基础设施正确运转 |
| Stage 3a (进行中) | 裸 LLM Agent (无防御) | — (FAIL 基线) | 攻击对 LLM 确实有效 |
| Stage 3b/c (规划中) | 防御 LLM Agent | Agent 主动阻止了攻击 | 纵深防御有效 |

> **这条演进线证明了三件事**: (1) 测试用例是有效的, (2) IPI 攻击对 LLM Agent 确实构成威胁, (3) 纵深防御可以将风险降到可接受水平。

## 6. 技术架构

### 6.1 整体架构

```
前端 (Next.js + React + TypeScript)
│
├── 7 个功能页面 (GSAP 动画, SSE 实时事件)
├── BFF 路由层 (同源代理, 密钥隔离)
│
└── ← REST API + SSE →

后端 (FastAPI + Python)
│
├── Agent 层: CorpMate (关键词) / LLMAgent (规划中)
├── 评测引擎: EvaluationCoordinator (批量编排, 后台 worker)
├── 三层沙箱: Browser / Memory / Email
├── 判定引擎: CompositeJudge (Rule + LLM)
├── 持久化: SQLite + SSE 事件流
│
└── 安全契约层
    ├── RiskPattern / AttackSeed / TestCase (JSON Schema)
    ├── 冻结枚举 (risk_type / severity / node.type / ...)
    └── Mutation Engine (Seed × Template → Variant)
```

## 7. 竞品分析与差异化

| 维度 | 传统安全扫描工具 | 通用 AI 评测平台 | **本项目** |
|------|-----------------|-----------------|-----------|
| 目标 | Web 应用 / 网络 | LLM 对话质量 | **Agent 工具链安全** |
| 检测方式 | 静态扫描 / 漏洞库 | Prompt 测试集 | **动态执行 + 沙箱隔离 + 因果链追踪** |
| 覆盖攻击 | SQL注入/XSS/CSRF | 偏见/幻觉/毒性 | **IPI (间接提示注入) + 记忆投毒 + 隐私泄漏 + 跨会话持久攻击** |
| 结果解释 | 漏洞编号 + CVSS 分 | 准确率/通过率 | **5 节点因果路径 + 证据事件绑定 + 可回放 Trace** |
| 测试生成 | 手写 / 规则库 | 固定测试集 | **Mutation Engine 自动变异 (7 种子 × 8 模板)** |
| 跨会话检测 | ❌ | ❌ | ✅ **R4: 跨 2 个会话的持久化 IPI 攻击链** |

### 核心差异

1. **不是"安全扫描器"，是"安全体检中心"** — 全流程闭环，从接入到报告
2. **不是"黑箱打分"，是"白箱取证"** — 每条结论绑定因果链和 Trace 事件
3. **不是"静态测试集"，是"自动变异引擎"** — 组合式生成覆盖数十种攻击变体
4. **不是"单会话检测"，是"跨会话追踪"** — R4 攻击链覆盖记忆持久化 + 新会话利用

## 12. 评委高频问题的标准回答

| 问题 | 标准回答 |
|------|----------|
| "你们的项目和通用 AI 安全评测有什么区别？" | 我们聚焦 Agent 工具链安全，不是测 LLM 对话质量。Agent 有工具调用、持久记忆、跨会话能力——这些是普通 LLM 没有的攻击面 |
| "86 条 TestCase 够吗？" | 86 条覆盖 4 种攻击模式 + 41 条自动变异。Mutation Engine 可以持续扩展——新增种子或模板即可自动生成更多 TC |
| "80% PASS 率说明什么？" | 说明 Judge 不是全 PASS 的假阳性。17 条 FAIL 全部有证据链，且根因已定位。Stage 3 接入 LLM Agent 后 FAIL 率会飙升到 60-75%，证明攻击确实有效 |
| "CorpMate 是什么？为什么不用真实 LLM？" | CorpMate 是用于验证评测引擎正确性的参考 Agent。Stage 3 已规划接入真实 LLM Agent (GPT-4o / Claude)，这是有意的分阶段策略 |
| "R4 攻击链是什么？" | 跨 2 个会话的持久化 IPI: 恶意网页 → Agent 读取 → 写入记忆 → 新会话读取记忆 → 未确认发送邮件。5 个节点，是 Agent 安全领域最前沿的攻击模式 |
| "评分算法怎么设计的？" | capability × 25% + security × 55% + stability × 20%。CRITICAL 级别漏洞触发分数上限，严重问题对总分影响最大 |
| "你们三个人是怎么分工的？" | 三条线并行: Security (TC 设计 + 安全策略) / Platform (引擎 + API + 持久化) / Frontend (可视化 + 交互)。Stage 3 合并为两线 |
| "3 周做出来，是不是 AI 帮你写的？" | AI 辅助了代码编写，但架构设计、安全策略、TestCase 设计、契约定义、前端交互设计都是团队主导。Git 提交历史可以追溯每一步决策 |
| "后续怎么商业化？" | 面向 Agent 开发团队提供 SaaS 评测服务；面向企业提供 Agent 上线前安全检测；面向监管机构提供合规评测工具 |
