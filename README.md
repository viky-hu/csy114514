# Agent 安全评估平台前端

## 本系统使用的技术栈

本系统前端采用现代 React 应用架构，重点服务于 Agent 安全评估过程中的结构可视化、攻击过程呈现和风险报告表达。

- **应用框架**：Next.js，使用 App Router 组织页面、布局、接口与功能窗口。
- **开发语言**：TypeScript，用于定义 Agent 节点、攻击事件、评估状态、风险报告等核心数据结构。
- **UI 框架**：React 函数组件，按功能窗口和业务模块进行组件化拆分。
- **样式体系**：项目自有 CSS、CSS Variables 与特性级样式文件，保证安全评估界面的视觉风格统一、可控、易于迭代。
- **图标系统**：lucide-react，用于工具栏、状态标识、风险等级、攻击路径、节点类型等界面符号。
- **交互控件**：Radix UI 轻量 Headless 组件，用于切换、分组、弹层等需要可访问性的交互场景。
- **动画系统**：GSAP 与 @gsap/react，用于攻击链路演进、节点状态变化、风险验证过程、评估进度等时间线动画。
- **图形与空间可视化**：Three.js、React Three Fiber、Drei、Postprocessing、OGL，用于构建沉浸式结构图、攻击图和安全态势视觉层。
- **数据可视化能力**：D3 Geo 等数据处理能力，用于复杂拓扑、路径映射、节点布局和图形数据转换。
- **数据校验**：Zod，用于前端接入配置、SSE 事件、评估结果、风险报告数据结构的运行时校验。
- **数据与服务集成**：Prisma Client 作为平台数据层集成基础，配合后端保存评估任务、Agent 资产、攻击证据和报告结果。
- **包管理与工程化**：pnpm/Corepack 工作流，使用项目既有脚本进行开发、构建、类型检查和质量验证。

## 本系统的宗旨

Agent 安全评估平台的前端不是一个普通的管理后台，而是一个面向用户、评委和安全分析人员的可解释安全可视化系统。它的核心目标是把复杂的 Agent 安全技术转译成可以被直观看懂、可以被追踪验证、可以被复盘讨论的界面语言。

系统围绕三个关键问题展开：

1. **我的 Agent 是什么结构？**
   通过 Anatomy 可视化展示 Agent 的组成方式，包括入口 Source、核心 Agent、外部 Tool、Memory、Data、权限边界和潜在危险 Sink。用户不需要阅读大量配置或日志，也能快速理解被测 Agent 的运行骨架。

2. **平台正在怎么攻击它？**
   通过实时评估流、攻击路径高亮和动态攻击动画，让用户看到攻击从哪里进入、经过哪些节点、调用了哪些工具、触发了哪些判断，以及如何从 Potential Risk 逐步演化为 Validated Attack。

3. **到底哪里有问题？**
   通过风险报告把攻击链路、证据片段、判断依据、影响范围和缓解建议组织起来，让结果不只是一个分数或告警，而是一份能够指导修复的安全分析结论。

因此，本系统的宗旨是：**让 Agent 安全评估从“黑盒测试结果”变成“可观察、可解释、可复现、可修复”的完整安全认知过程。**

## 本系统的功能分区构思

### 1. Agent 接入区

Agent 接入区用于创建评估对象，支持三种接入方式：

- **API 接入**：填写 Endpoint、鉴权方式、请求协议、输入输出 Schema，用于评估线上 Agent 服务。
- **Docker 接入**：提交镜像地址、启动命令、环境变量、网络策略，用于隔离运行和沙箱化测试。
- **GitHub 接入**：绑定仓库地址、分支、启动脚本和配置文件，用于从源码构建并分析 Agent。

该区域需要清晰展示接入状态、连通性检查、配置校验结果和可评估范围，帮助用户确认平台已经正确理解并接管被测 Agent。

### 2. Anatomy 结构可视化区

结构可视化区回答“我的 Agent 是什么结构”。它以图形节点和边的方式呈现 Agent 的组成关系：

- **Source**：用户输入、外部请求、Webhook、文件上传、消息队列等入口。
- **Agent**：规划器、执行器、模型调用、推理链路、任务调度模块。
- **Tool**：搜索、浏览器、数据库、Shell、代码执行器、第三方 API 等外部能力。
- **Memory**：短期记忆、长期记忆、向量库、会话上下文。
- **Data**：业务数据、用户数据、密钥、配置、文档、知识库。

每个节点应具备安全状态标识，例如 Unknown、Safe、Potential Risk、Under Test、Validated Attack、Mitigated。节点之间的边用于表达调用关系、数据流、权限传递和风险传播方向。

### 3. 攻击图与路径区

攻击图区域用于展示平台发现或验证的攻击链路。它需要从入口到危险 Sink 形成一条可追踪路径：

- 高亮攻击入口，例如恶意 Prompt、污染文档、伪造 API 回调或被操控的工具返回值。
- 展示中间传播节点，例如 Agent 推理、Memory 写入、工具调用、权限升级、上下文污染。
- 标记危险 Sink，例如敏感数据泄露、任意代码执行、越权工具调用、外部请求转发、持久化污染。
- 区分潜在风险路径与已验证攻击路径，避免用户把猜测和证据混在一起。

该区域应支持路径切换、节点聚焦、证据定位和攻击阶段回放，使用户能从整体态势下钻到具体问题。

### 4. 实时评估过程区

实时评估区通过 SSE 事件流展示平台正在执行的测试过程。它应当像一个可读的安全执行台，而不只是日志滚动窗口。

核心事件包括：

- 评估任务启动、阶段切换、进度更新。
- 测试用例生成、Payload 注入、上下文构造。
- Agent 响应、模型判断、工具调用、Memory 读写。
- 安全策略命中、风险假设建立、验证步骤执行。
- 攻击成功、攻击失败、需要人工确认、评估完成。

界面上应同时提供时间线、事件流、当前阶段状态、关键证据摘录和工具调用摘要，让用户能理解平台“正在做什么”和“为什么这么判断”。

### 5. 攻击动画演示区

攻击动画区用于把抽象攻击过程转化成可感知的动态演进。它应重点表现风险从出现到验证的过程：

- **Potential Risk**：平台识别到可疑入口、可疑能力组合或可疑数据流。
- **Probe**：平台开始构造测试样本，对节点或路径进行探测。
- **Propagation**：攻击输入在 Agent、Tool、Memory、Data 之间传播。
- **Trigger**：危险能力被调用，或敏感数据被访问。
- **Validated Attack**：平台获得证据，确认攻击链路成立。

动画不应只是装饰，而应与真实评估事件绑定：当 SSE 收到关键事件时，图上的节点、边、状态和证据面板同步变化，形成“数据驱动的攻击回放”。
