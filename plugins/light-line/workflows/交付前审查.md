# 交付前审查 Workflow

## 适用场景

当一次功能、修复、重构或计划实践准备交付前使用。

## 目标效果

按仓库根规则完成三项强制交付：功能归属声明、扩展性审查、必要重构；若模块职责变化，同步文档门禁。

## 应加载的 Skills

- `repo-delivery-governance`
- `frontend-stack-mistake-book`
- `frontend-component-mistake-book`
- 与本次改动窗口或计划对应的治理/实践 skill

## 执行步骤

1. 汇总改动影响面：主责文件、协同文件、用户可见行为、接口或模块职责变化。
2. 检查扩展成本：是否新增硬编码、重复逻辑、跨模块污染或未来难以替换的边界。
3. 判断是否需要当次重构：重复逻辑、边界污染、硬编码扩散不能留到以后。
4. 如果模块职责变化，更新 `docs/architecture/modules-index.md` 和 `docs/architecture/extension-review-checklist.md`。
5. 运行必要验证，至少包含类型检查、相关测试或可解释的替代验证。
6. 最终回复必须明确功能归属、扩展性审查、必要重构、验证结果和残余风险。

## 验收标准

- 用户能从交付说明看懂“哪个文件负责什么”。
- 扩展性审查不是只说没报错，而是说明边界是否稳定。
- 没有把明显应当重构的问题留作以后。
- 文档同步门禁被正确执行或明确说明不适用。
